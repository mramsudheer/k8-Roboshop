A security context defines the operating system security settings, such as controlling whether a process can gain more privileges than its parent process, restricting write access to container’s root filesystem, file-like object access permissions based on `uid` and `gid`, `Linux capabilities`, `SELinux role`, etc., applied to a `pod` or individual `container`. The constraints imposed by a security context are designed to achieve the following goals:<br><br>
&emsp;1.&emsp;Ensure a clear isolation between container and the underlying host it runs on<br>
&emsp;2.&emsp;Limit the ability of the container to negatively impact the infrastructure or other containers<br><br>
**Understanding Kubernetes Security Contexts**<br><br>
A security context defines privilege and access settings for a `pod` or `container`. It can be configured at the `pod level`(`PodSecurityContext`), affecting all `containers` in the `pod`, or at the `individual container level`(`SecurityContext`), overriding pod-level settings where necessary.<br>
Equivalent fields at the container level take precedence over the fields specified in the `PodSecurityContext`. One thing to note is that `PodOS` field in the `PodSpec` can restrict some security context fields at both pod and container level.<br><br>
We can define a Security Context on the `pod level`, which means that the settings are assigned to `all containers` in the `pod`. Or the Security Context can be assigned to the `individual containers` in the `pod`.
Also, please be aware that it is not possible to assign all settings of a Security Context on both the `pod level` and the `container level`.<br>
Some can only be assigned to the `pod`, some only to the `containers`, and others on both. <br>If a Security Context with conflicting settings is defined on the `pod level` and on the `container level`, the settings from the `container level` counts.<br><br>
​&emsp;1.&emsp;**Pod-Level Only**<br>These settings apply to the entire pod infrastructure, network namespaces, and shared storage volumes. They cannot be defined inside individual container blocks.<br>
​&emsp;•&emsp;**fsGroup:** Defines a special supplemental group ID for volume mounts.<br>
​&emsp;•&emsp;**fsGroupChangePolicy:** Controls how volume ownership and permissions change.<br>
​&emsp;•&emsp;**seccompProfile:** Sets the profile for the entire pod (can also be overridden per container).<br>
​&emsp;•&emsp;**supplementalGroups:** Adds extra group IDs for all containers.<br>
​&emsp;•&emsp;**sysctls:** Configures namespaced kernel parameters for the pod.<br><br>
​&emsp;2.&emsp;**Container-Level Only**<br>These settings apply strictly to the processes inside a specific container image and interact directly with Linux capabilities and file systems.<br>
​&emsp;•&emsp;**capabilities:** Adds or drops specific Linux capabilities (e.g., `NET_ADMIN`).<br>
​&emsp;•&emsp;**privileged:** Runs the container with root privileges on the host node.<br>
​&emsp;•&emsp;**procMount:** Type of proc mount for the container (Default or Unmasked).<br>
​&emsp;•&emsp;**readOnlyRootFilesystem:** Forces the container root filesystem to be read-only.<br>
​&emsp;•&emsp;**allowPrivilegeEscalation:** Controls if a process can gain more privileges than its parent.
​&emsp;3.&emsp;**Shared (Both Pod and Container Level)**<br>These settings can be declared at either level. If configured at both levels, the container's value overrides the pod's value.<br>
​&emsp;•&emsp;**runAsUser:** The specific User ID (UID) used to run the container process.<br>
​&emsp;•&emsp;**runAsGroup:** The Primary Group ID (GID) used to run the container process.<br>
​&emsp;•&emsp;**runAsNonRoot:** Forces the container to run as any user except root (UID 0).<br>
​&emsp;•&emsp;**seLinuxOptions:** Sets the SELinux labels for the processes.<br>
​&emsp;•&emsp;**windowsOptions:** Specifies Windows-specific configuration options.<br><br>
**Container-Level Security Contexts:** A Container-Level Security Context applies specifically to individual containers within a pod. Here are some key aspects:<br><br>
&emsp;•&emsp;**Run as Non-Root:** This setting ensures that the container does not run processes as the root user.<br>
&emsp;•&emsp;**Read Only Root Filesystem:** You can make the container’s root filesystem read-only, which helps prevent malicious write operations.<br>
&emsp;•&emsp;**Control over Privileges:** Control capabilities like whether a container can bind to well-known ports.<br><br>
**Pod-Level Security Contexts:** Pod-Level Security Contexts apply to the entire pod and all the containers within it. Some key settings include:<br><br>
&emsp;•&emsp;**Security Policy for All Containers:** Define a common policy for all containers in the pod.<br>
&emsp;•&emsp;**Volume and File Permissions:** Set permissions for volumes mounted into the pod, ensuring secure data handling.<br><br>
**Security Context settings** <br>
&emsp;•&emsp;capabilities<br>
&emsp;•&emsp;privileged<br>
&emsp;•&emsp;runAsNonRoot and runAsUser<br>
&emsp;•&emsp;allowPrivilegeEscalation<br>
&emsp;•&emsp;readOnlyRootFilesystem<br>
&emsp;•&emsp;seccomp<br>
Additionally, we will discuss these settings that should be considered to enhance the security of a pod further:<br><br>
&emsp;•&emsp;hostNetwork, hostPID and hostIPC<br>
&emsp;•&emsp;AppArmor<br>
&emsp;•&emsp;resource requests and limits<br>
&emsp;•&emsp;hostPath<br><br>

**Non-privileged pod with non-root user**<br><br>
This example uses a different image as it needs the `iputils` package.<br>

```hcl

  name: non-root-user-pod-demo

    runAsNonRoot: true
```

```hcl
    runAsGroup: 3000

  - name: demo-volume
    emptyDir: {}

  - name: non-root-user-demo
```

```hcl
    kubectl create -f non-root-user-pod.yaml
    kubectl exec -it non-root-user-pod-demo -- sh
```

**Enforce read-only root file system**<br><br>
Read-only root file system helps to enforce immutable infrastructure strategy. Most containers are stateless and should not need to write to the local file system. Those containers that do, should write on the mounted volumes that persist the container restart or termination.<br><br>
Ensuring container root file system is immutable and employing a verified boot mechanism offers protection against potential attackers gaining control over the host machine through permanent local changes. It also safeguards the host system from malicious binaries attempting to unauthorised writes to the host file system.<br><br>
At the container level, the securityContext includes a parameter called `readOnlyRootFilesystem`, which, when set to `true`, mounts the root file system in read-only mode. To demonstrate this, let's modify the initial example to set the root file system as read-only and subsequently test its behaviour.<br>
`read-only-root-fs.yaml` <br>
```hcl
apiVersion: v1
kind: Pod
metadata:
  name: read-only-root-fs-pod-demo
spec:
  containers:
  - name: read-only-root-fs-demo
    image: redhat/ubi8
    command: [ "tail", "-f", "/dev/null" ]
    securityContext:
      readOnlyRootFilesystem: true
```
```hcl
# Create the pod
kubectl create -f read-only-root-fs.yaml

# Attempt to create a file
kubectl exec -it read-only-root-fs-pod-demo -- touch aa    
touch: cannot touch 'aa': Read-only file system
command terminated with exit code 1
```

**Security Context settings**<br>
&emsp;1.&emsp;**The "capabilities" setting**<br><br>
The Linux capabilities feature exists for quite a while now, it was introduced in the 2.2 kernel in the year 1999. With Linux capabilities, it is no longer necessary to give a process either all permissions or no permissions at all. Instead, it is possible to assign a process a defined set of permissions, called a "capability".<br>
​​​​​​​But how does this relate to Kubernetes? Well, a container in Kubernetes is basically a process running on the host system. So, we can limit the permissions of a container with the use of Linux capabilities. Maybe now you wonder what happens if you do not define capabilities for your pod? Good question! Let's find out.<br><br>
In the following example, we first create a pod, then we log into the running pod by using the `kubectl exec` command. After finding out the process ID of the container, we check the capabilities of the pod. To decode the displayed capabilities, we use the program `"capsh"`.<br>
```hcl
// create a new pod
$ kubectl run test-pod --image=nginx
pod/test-pod created
// log into the created pod
$ kubectl exec -it test-pod -- bash
// get pid of running process
root@test-pod:/# echo $$
45
// get capabilities of running process
root@test-pod:/# cat /proc/45/status | grep CapEff
CapEff: 00000000a80425fb
root@test-pod:/# exit
exit
// decode capabilities
$ capsh --decode=00000000a80425fb
0x00000000a80425fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap
```
We can see that the default capabilities (which depend on the used container runtime) of a container are quite a lot. And probably not all of them are needed. So how can we limit the capabilities of the container? Here we can use the "`capabilities`" setting in the Security Context.<br>
**Best practice: Drop all capabilities**<br><br>
The best practice in regard to capabilities is to drop all capabilities in a pod definition if possible. Here is an example how this looks like:<br>
```hcl
# pod definition with all capabilities dropped
apiVersion: v1
kind: Pod
metadata:
  name: no-caps
  labels:
    app: no-caps
spec:
  containers:
    - name: no-caps
      image: my-image
      securityContext:
        capabilities:
          drop:
            - all
```
```hcl
$ k exec -it no-caps -- sh
/ # echo $$
7
/ # cat /proc/7/status | grep CapEff
CapEff: 0000000000000000
```
When we check the assigned capabilities of the pod, we can see that this pod does not have any. ​​​​​​​But what if the pod needs one or more capabilities? In that case, we can drop all capabilities and then add only the needed ones:<br>
```hcl
# pod definition with only the "cap_net_bind_service"
apiVersion: v1
kind: Pod
metadata:
  name: cap-net-bind-service
  labels:
    app: cap-net-bind-service
spec:
  containers:
    - name: cap-net-bind-service
      image: image-name
      securityContext:
        capabilities:
          drop: ["all"]
          add: ["NET_BIND_SERVICE"]
```
```hcl
k exec -it cap-net-bind-service -- sh
/ # echo $$
7
/ # cat /proc/7/status | grep CapEff
CapEff: 0000000000000400
/ # exit
capsh --decode=0000000000000400
0x0000000000000400=cap_net_bind_service
```
Here we see that this pod only has the capability "cap_net_bind_service" assigned.<br><br>
&emsp;2.&emsp;**The "privileged" setting**<br><br>
We talked about capabilities in the previous section, but how is this connected with the `privileged` setting in the Security Context?<br>
​​​​​​​The first question is what capabilities a pod has if we do not set `privileged`? If privileged is not set, it defaults to `false`, which is good news in regard to security. But does this mean the pod has no capabilities assigned at all? And what if we set `privileged: true`? Let's check.<br>
```hcl
apiVersion: v1
kind: Pod
metadata:
  name: privileged-pod
spec:
  containers:
  - name: nginx
    image: nginx
    securityContext:
      privileged: true
```
```hcl
kubectl exec -it privileged-pod -- bash
root@no-capabilities-pod:/# echo $$
72
root@no-capabilities-pod:/# cat /proc/72/status | grep CapEff
CapEff: 0000003fffffffff
root@no-capabilities-pod:/# exit
exit
capsh --decode=0000003fffffffff
0x0000003fffffffff=cap_chown,cap_dac_override,cap_dac_read_search,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_linux_immutable,cap_net_bind_service,cap_net_broadcast,cap_net_admin,cap_net_raw,cap_ipc_lock,cap_ipc_owner,cap_sys_module,cap_sys_rawio,cap_sys_chroot,cap_sys_ptrace,cap_sys_pacct,cap_sys_admin,cap_sys_boot,cap_sys_nice,cap_sys_resource,cap_sys_time,cap_sys_tty_config,cap_mknod,cap_lease,cap_audit_write,cap_audit_control,cap_setfcap,cap_mac_override,cap_mac_admin,cap_syslog,cap_wake_alarm,cap_block_suspend,cap_audit_read
```
We can see that a pod with `privileged: true` has all capabilities assigned. This is the same, as if we would add all capabilities via the "capabilities" setting in the Security Context. To run your pod as `privileged: true` means that the container has full root privileges on the host system and can access all capabilities provided by the kernel. This basically disable most security mechanisms and should be avoided if possible.<br><br>
**Best practice: "privileged: false"** <Br><br>
It is best practice to set `privileged: false`. Now let's see what capabilities a pod with the setting `privileged: false` has.
```hcl
apiVersion: v1
kind: Pod
metadata:
  name: unprivileged-pod
spec:
  containers:
  - name: nginx
    image: nginx
    securityContext:
      privileged: false
```
```hcl
kubectl exec -it unprivileged-pod -- bash
echo $$
45
cat /proc/45/status | grep CapEff
CapEff: 00000000a80425fb
exit 
$ capsh --decode=00000000a80425fb
0x00000000a80425fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap
```
We can see that even if we set `privileged: false`, the pod has the same capabilities as the pod with the default settings in the "capabilities" section above. Combine `privileged: false` with dropping as many capabilities as possible, to avoid having a pod with too many privileges.<br><br>
&emsp;3.&emsp;**The "runAsNonRoot" and "runAsUser" settings**<br><br>
Before we get into details, let us start with talking about what it means to run a container as root. Does this mean the user has automatically root rights on the host system? Fortunately no, because *Docker provides container isolation mechanisms*. But nevertheless, a root inside a container is the same as the root account on the host system. Which means that if an attacker could break out of the container, he would be root on the host system. A container breakout could happen because of a vulnerability in your application, in the Docker runtime, or in the Linux kernel.<br><br>
Therefore, it is strongly recommended to only run a container as non-root whenever possible.<br>
**Best practice: Run container as non-root**<br><br>
It is best practice to set `runAsNonRoot: true` and also define the user by setting runAsUser to a user other than root (which has user ID 0). If not defined, the container process runs as the default user of the used image.<br>
Please be aware that if you configure `runAsNonRoot: true`, but you do not define a user with `runAsUser`, and the default user is root, the container will not run.<br><br>
In the following example, we set `runAsNonRoot: true` and define a user other than root with runAsUser. Then we check the user id of the container.<br>
```hcl
apiVersion: v1
kind: Pod
metadata:
  name: run-as-user
spec:
  containers:
  - name: run-as-user
    image: alpine:3.18.0
    command: ['/bin/sleep', '1d']
    securityContext:
       runAsUser: 1000
       runAsNonRoot: true
```
```hcl
 k exec -it run-as-user -- sh
~ $ id
uid=1000 gid=0(root) groups=0(root)
```
&emsp;4.&emsp;**The "allowPrivilegeEscalation" settings**<br><br>
Another important setting is `allowPrivilegeEscalation`. If we do not define this setting it defaults to true, which is a problem because it means that it is possible for your process in the pod to gain more privileges than its parent.<br>
Also, if your container runs as `privileged` or has the "cap_sys_admin" capability assigned, `allowPrivilegeEscalation` is always true.<br>
**Best practice: set "allowPrivilegeEscalation" to false**<br><br>
Set `allowPrivilegeEscalation: false` to prevent containers from escalating privileges, such as by using setuid or setgid to change their effective user or group ID.
```hcl
apiVersion: v1
kind: Pod
metadata:
  name: privilege-escalation-not-allowed
spec:
  containers:
  - name: nginx
    image: nginx
    securityContext:
      allowPrivilegeEscalation: false
```
&emsp;5.&emsp;**The "readOnlyRootFilesystem" setting**<br><br>
The `readOnlyRootFilesystem` setting defines if a process is allowed to modify the filesystem of the container it runs in. By default a process can change the filesystem of it's container, because this setting defaults to `false`.<br><br>
**Best practice: Set "readOnlyRootFilesystem" to "true"**<br><br>
Best practice is to set `readOnlyRootFilesystem: true`. If the process needs to write data somewhere, instead of setting `readOnlyRootFilesystem` to `false`, consider mounting an emptyDir to write data to. A process can write to an `emptyDir`, even if `readOnlyRootFilesystem` is set to `true`.<br>
```hcl
apiVersion: v1
kind: Pod
metadata:
  name: read-only-root-fs
spec:
  containers:
  - name: alpine
    image: alpine:3.18.0
    command: ['/bin/sleep', '1d']
    securityContext:
      readOnlyRootFilesystem: true
```
```hcl
$ k exec -it read-only-root-fs -- sh
/ # touch testfile
touch: testfile: Read-only file system
```
**Tip**<br><br>
If you want to have pods that are immutable, which means that they cannot be changed during runtime, combine the following two settings in the Security Context:<br>
```hcl
securityContext:
​​​​​​​  readOnlyRootFilesystem: true
  ​​​​​​​privileged: false
```
&emsp;6.&emsp;**The "seccomp" setting**<br><br>
You can use seccomp to restrict the available system calls for your application and by doing so, decrease your application's attack surface. Seccomp is an abbreviation for "secure computing mode" and is a built-in Linux security feature.<br>
Seccomp is part of the Security Context. Be aware, that it is not possible to use seccomp if your containers run as privileged.<br><br>
The following three seccomp types can be defined in the Security Context:<br><br>
**unconfined**<br><br>
​&emsp;•&emsp;If you do not want to use seccomp (which is not recommended, by the way), you can select the type `unconfined`. Also `unconfined` is used as the default type if you do not specify seccomp in the Security Context. ​​​​​​​<br><br>
**RuntimeDefault**<br><br>
​&emsp;•&emsp;If you want to use seccomp without the need to define custom profiles, `RuntimeDefault` is the right choice for you. As the name already suggests, `RuntimeDefault` uses the default seccomp profile of your Container Runtime, e.g., the Docker default seccomp profile or the containerd default seccomp profile.<br><br>
**Localhost**<br><br>
​&emsp;•&emsp;If you want to use a custom profile for seccomp, you can do this by creating your own seccomp profiles. The seccomp profiles have to be stored in the "/var/lib/kubelet/seccomp/" directory.<br><br>
`Seccomp` is also supported on EKS, GKE and AKS.<br><br>
**Best practice: Use seccomp type "RuntimeDefault" or "Localhost"**<br><br>
```hcl
# RuntimeDefault profile
apiVersion: v1
kind: Pod
metadata:
  name: seccomp-pod
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: nginx
    image: nginx
```
```hcl
# Localhost profile
securityContext:
  seccompProfile:
    type: Localhost
    localhostProfile: profiles/audit.json
```

**Additional Pod Security Settings**<br><br>
In the sections above, we talked about settings in the Kubernetes Security Context. But there are additional settings that have to be considered to secure a Kubernetes workload, although they are not part of the Security Context.<br><br>
Therefore, in this section we will take talk about hostNetwork, hostPID and hostIPC, AppArmor, resource requests and limits and the `hostPath` setting.<br><br>
**hostNetwork, hostPID and hostIPC**<br><br>
Host namespaces, like the network namespace (hostNetwork), the Process ID namespace (hostPID) or the Inter-process communication namespace (hostIPC), allow access to shared information on the underlying host. Let's see what this means in regard to Kubernetes.<br><br>
​&emsp;•&emsp;If **hostNetwork** is allowed, the pod can use the node network namespace. This gives the pod access to the loopback device, services listening on localhost, and could be used to snoop on network activity of other pods on the same node.<br><br>
​&emsp;•&emsp;If **hostPID** is allowed, the pod containers can share the host process ID namespace. This allows the pod e.g., to see all processes running on the host, including processes running inside other pods, and to view all environment variables of each pod on the host.<br><br>
​&emsp;•&emsp;if **hostIPC** is allowed, the pod can use the host’s inter-process communication mechanisms (shared memory, semaphore arrays, message queues, etc.). This enables the pod to read/write to mechanisms, if any other process on the host uses the same mechanisms.<br><br>
As we saw above, from security perspective hostNetwork, hostPID and hotIPC should be disabled. The default for all host namespaces is false, so not defining it is sufficient, though it can also be explicitly set to false if desired.<br>
```hcl
spec:
   hostNetwork: false
   hostPID: false
   hostIPC: false
```
**AppArmor**<br><br>
*AppArmor* is a built-in Linux security module, that can be used to restrict a program to a set of files, capabilities and network access.<br>
If *AppArmor* is loaded onto the Node, it can be defined in the pod definition. You can define your own *AppArmor* profile with `Localhost`, or you can use the `RuntimeDefault` *AppArmor* profile.<br>
```hcl
securityContext:
  appArmorProfile:
    type: <profile_type>
```
**Resource requests and limits**<br><br>
Since availability is also an important part of Security, it is best practice to set resource requests and limits for Kubernetes Resources.<br><br>
​&emsp;•&emsp;For **CPU**, it is recommended to set only the resource request, but no limit.<br>
Many people think you need `CPU limits` on Kubernetes but this isn't true. In most cases, Kubernetes CPU limits do more harm than help.<br>
**Example**<br><br>
Imagine a single server node that has `4 Cores of CPU` available. On this server, you run two applications: an `API Service` and a `Background Report Worker`.<br>
**Scenario A: With CPU Limits (The Problem)**<br><br>
You set a limit of `1 Core` for the `Report Worke`r so it doesn't slow down the API.<br>
&emsp;1.&emsp;**The Situation:** It is midnight. The API Service is completely idle, using 0 Cores. 4 Cores are sitting empty.<br>
&emsp;2.&emsp;**The Event:** A user triggers a massive data report.<br>
&emsp;3.&emsp;The Result:** The Report Worker hits its `1 Core limit` instantly. It takes `30 minutes` to finish the report, heavily throttling its own performance. Meanwhile, 3 Cores of CPU power sit completely wasted and unused right next to it.<br><br>
**Scenario B: Without Limits, With Requests (The Solution)**<br><br>
Instead of a maximum limit, you give both apps a guaranteed minimum reservation (`CPU Requests`):<br>
​&emsp;•&emsp;**API Service Request:** 2 Cores (Guaranteed)<br>
​&emsp;•&emsp;**Report Worker Request:** 1 Core (Guaranteed)<br>
&emsp;1.&emsp;**The Situation:** It is midnight. The API Service is idle (using 0 Cores).<br>
&emsp;2.&emsp;**The Event:** The massive data report is triggered.<br>
&emsp;3.&emsp;**The Result:** Because there is no artificial limit, the Report Worker safely "bursts" and borrows the idle CPU. It hogs all `4 Cores` and finishes the report in just `7 minutes`.<br>
&emsp;4.&emsp;**The Protection:** If a sudden rush of users hits the API Service while the report is running, Kubernetes instantly steps in. It forces the Report Worker to give back the CPU until it hits its 1-Core minimum, handing the 2 Cores back to the API Service.<br><br>
**Preventing CPU throttling and insufficient CPU without limits**<br><br>
Many people think you need limits to prevent one pod from interfering with another pod. This is not true! **You can remove Kubernetes CPU limits and still prevent a CPU hungry pod from causing CPU starvation!** The trick is to just define CPU requests.<br>
*Pods always get the CPU requested by their CPU request!* (They can take advantage of excess CPU too if they have no limit.)<br><br>
Disable your CPU limits! If you give all your K8s pods accurate CPU requests, then no-one can throttle them because CPU is reserved for them if they need it. This has nothing to do with limits.<br><br>
**Kubernetes Requests vs Limits**<br><br>
Lets summarize the difference between CPU limits and requests in a table:<br>
I'm assuming for simplicity that either all pods have CPU limits or none have them. The same is true for CPU requests. This makes everything simpler to reason about.<br><br>
**Best practices for CPU limits and requests on Kubernetes**<br>
Lets summarize:<br>
​&emsp;•&emsp;Use CPU requests for everything<br>
​&emsp;•&emsp;Make sure they are accurate<br>
​&emsp;•&emsp;Do not use CPU limits.<br><br>
**What about memory limits and requests?**<br><br>
On Kubernetes, the best practice is to set memory **limit=request**. <br>
Memory is different because it is non-compressible - once you give memory you can't take it away without killing the process.<br>
recommendation is:<br><br>
​&emsp;•&emsp;Always use memory limits<br>
​&emsp;•&emsp;Always use memory requests<br>
​&emsp;•&emsp;Always set your memory requests equal to your limits<br><br>
**The difference between memory limits and CPU limits on Kubernetes**<br><br>
CPU is fundamentally different than memory. CPU is a compressible resource and memory is not. In simpler terms, you can give someone spare CPU in one moment when it's free, but that does **not** obligate you to continue giving them CPU in the next moment when another pod needs it. There is no downside to giving away idle CPU, because it's easy and non-violent to reclaim it.<br><br>
Why is memory different than CPU on Kubernetes? Because memory is a non-compressible resource. Once you give a pod memory, you can only take it away by killing the pod. This is the cause of OOM Kills.<br><br>
**Best Practices for Kubernetes Limits and Requests**<br><br>
This is why I always advise:<br><br>
&emsp;1)&emsp; Always set memory limit == request<br>
&emsp;2)&emsp; Never set CPU limit<br>
(for locally adjusted values of "always" and "never")<br>
```hcl
---
apiVersion: v1
kind: Pod
metadata:
  name: proper-resource-configuration
spec:
  containers:
  - name: app
    image: this.part-isnt.interesting/robustadev:keepreading
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "64Mi" # the memory limit equals the above request!
        # no cpu limit! this is excluded on purpose
```
**Symptoms of OOMKilled Kubernetes Pods**<br><br>
How do you know if you're experiencing OOMKills on Kubernetes anyway? Here are the obvious signs:<br><br>
&emsp;1.&emsp;Containers and processes with Error code 137<br>
&emsp;2.&emsp;Running **kubectl get pods** and seeing OOMKilled in the status column<br>
&emsp;3.&emsp;Running **kubectl describe pod** and seeing a Command terminated with exit code 137 message<br>
&emsp;4.&emsp;Prometheus alerts like **HostOomKillDetected** and **KubernetesContainerOomKiller** (these alerts are often copy-pasted from popular alert collections like Awesome Prometheus Alerts)<br>
&emsp;5.&emsp;Slack notifications about OOM Killed pods with Robusta's Prometheus-based Kubernetes monitoring<br><br>
How can you identify OOM Kills when you're **not** monitoring them directly? The symptoms will show up elsewhere. For example, pods might suddenly drop connections or crash without notice. When in doubt, look for **exit code 137** in the **kubectl describe pod** output. If a pod exited with code 137, it's an OOMKill for sure!<br><br>
**hostPath**<br><br>
With the `hostPath` setting, it is possible to mount a file or a directory from the host filesystem into you pod. If the host filesystem is mounted and the pod also has write access, there is a high risk of privilege escalation. A pod with such a configuration is able to traverse the host filesystem outside the specified path, to read data from other containers, and to abuse credentials of system services like the Kubelet.<br><br>
Therefore, it is best practice to avoid using hostPath whenever possible. If you really need access to the filesystem of the underlying host, do not mount the root directory, and set `readOnly: true` if possible.<br>
```hcl
volumeMounts:
   - mountPath: "/path/to/directory"
     name: demopath
     readOnly: true
```
