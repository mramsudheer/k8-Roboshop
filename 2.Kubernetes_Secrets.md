**What is a Kubernetes Secret?** <br><br>
A Kubernetes Secret is an object that stores sensitive data, such as passwords, OAuth tokens, and SSH keys. By using Secrets, you can keep sensitive information separate from your application code, reducing the risk of exposure.<br>

**Why Use Kubernetes Secrets?**<br>
&emsp;•&emsp;**Security:** Secrets provide a secure way to manage sensitive information.<br>
&emsp;•&emsp;**Decoupling Configuration:** Secrets allow you to separate sensitive configuration data from your application code and container images.<br>
&emsp;•&emsp;**Ease of Use:** Kubernetes provides built-in mechanisms to use Secrets in your pods and containers easily.<br><br>
**Creating Kubernetes Secrets(commandline, from file,with yaml)**<br>
&emsp;&emsp;Creating a Secret from Literal Values<br>
You can create a Secret from literal values directly from the command line.<br>
```hcl
    kubectl create secret generic my-secret --from-literal=username=my-user --from-literal=password=my-password
```
**Creating a Secret from a File**<br>
Secrets can also be created from files, where the file contents become the value of the Secret.<br>

**Example:** `username.txt` and `password.txt` <br>
```hcl
    echo -n 'my-user' > username.txt
    echo -n 'my-password' > password.txt

    kubectl create secret generic my-secret --from-file=username.txt --from-file=password.txt
```
**Creating a Secret from Multiple Files**
You can create a Secret from multiple files, with each file’s content stored under its filename as a key.<br>
```hcl
    kubectl create secret generic my-secret --from-file=./credentials/
```
**Creating a Secret with YAML** <br>
You can define a Secret in a YAML file and create it using kubectl apply.<br>

**Example:** `secret.yaml` <br>
```hcl
apiVersion: v1
kind: Secret
metadata:
  name: my-secret
type: Opaque
data:
  username: bXktdXNlcg==
  password: bXktcGFzc3dvcmQ=
```
To create the Secret: <br>
```hcl
    kubectl apply -f secret.yaml
```
**Encoding Secret Data** <br>
Kubernetes expects Secret data to be base64-encoded. You can encode your data using a base64 encoder.<br>
```hcl
echo -n 'my-user' | base64
# Output: bXktdXNlcg==

echo -n 'my-password' | base64
# Output: bXktcGFzc3dvcmQ=
```
**Using Kubernetes Secrets** <br>
&emsp;&emsp;**Using Secrets as Environment Variables** <br>
You can expose Secrets as environment variables in your pods.<br>

**Example:** Using Secret as Environment Variables<br>
```hcl
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
  - name: my-container
    image: my-image
    env:
    - name: USERNAME
      valueFrom:
        secretKeyRef:
          name: my-secret
          key: username
    - name: PASSWORD
      valueFrom:
        secretKeyRef:
          name: my-secret
          key: password
```
**Using Secrets as Volume Mounts** <br>
Secrets can also be mounted as volumes in your pods, allowing containers to access the secret data as files.<br>

**Example:** Using Secret as a Volume<br>
```hcl
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
  - name: my-container
    image: my-image
    volumeMounts:
    - name: secret-volume
      mountPath: /etc/secret
      readOnly: true
  volumes:
  - name: secret-volume
    secret:
      secretName: my-secret
```
**Using Secrets with Deployments** <br>
In a production environment, you typically use Secrets with Kubernetes Deployments.<br>

**Example:** Using Secret in a Deployment<br>
```hcl
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-container
        image: my-image
        env:
        - name: USERNAME
          valueFrom:
            secretKeyRef:
              name: my-secret
              key: username
        - name: PASSWORD
          valueFrom:
            secretKeyRef:
              name: my-secret
              key: password
```
**Best Practices for Kubernetes Secrets** <br>
&emsp;1.&emsp;**Encrypt Secret Data at Rest** <br>
Ensure that your Kubernetes cluster is configured to encrypt Secrets at rest. This adds an additional layer of security by protecting the Secret data stored in etcd.<br>

**Example:** Enabling Encryption at Rest<br>
```hcl
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
    - secrets
    providers:
    - aescbc:
        keys:
        - name: key1
          secret: <base64-encoded-secret>
    - identity: {}
```
Apply the encryption configuration by restarting the Kubernetes API server with the `--encryption-provider-config` flag pointing to your configuration file.<br>
&emsp;1.&emsp;**Use RBAC to Control Access** <br>
Use Role-Based Access Control (RBAC) to restrict access to Secrets. Only grant permissions to users or service accounts that need access to Secrets.<br>

**Example:** RBAC Policy for Secrets<br>
```hcl
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: secret-reader
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "list", "watch"]
```
```hcl
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-secrets
  namespace: default
subjects:
- kind: User
  name: your-username
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: secret-reader
  apiGroup: rbac.authorization.k8s.io
```
&emsp;3.&emsp;**Rotate Secrets Regularly** <br>
Regularly rotate your Secrets to minimize the risk of compromise. Update your Secrets and redeploy your applications to use the new values.<br>

**Example:** Rotating a Secret<br>
&emsp;•&emsp;Create a new Secret with the updated values.<br>
&emsp;•&emsp;Update your Deployment to reference the new Secret.<br>
&emsp;•&emsp;Roll out the updated Deployment.<br>
&emsp;4.&emsp;**Use External Secret Management Solutions** <br>
Consider using external secret management solutions like HashiCorp Vault, AWS Secrets Manager, or Azure Key Vault to store and manage your Secrets. Integrate these solutions with Kubernetes to inject Secrets into your pods securely. <br>

&emsp;5.&emsp;**Avoid Hardcoding Secrets** <br>
Do not hardcode Secrets in your application code or container images. Always use Kubernetes Secrets or environment variables to manage sensitive information.<br>

&emsp;6.&emsp;**Audit Secret Access**<br>
Regularly audit access to your Secrets to ensure that only authorized entities are accessing them. Use Kubernetes audit logs and monitoring tools to track access.

&emsp;7.&emsp;**Limit Secret Size** <br>
Keep Secrets small and manageable. Avoid storing large files or excessive data in Secrets. For large data, consider using ConfigMaps or external storage solutions.<br><br>

**Kubernetes External Secrets** <br><br>
ExternalSecrets provides a seamless solution to manage your secrets securely by integrating with secret providers like AWS Secrets Manager, HashiCorp Vault, and others. This guide will walk you through the installation ExternalSecrets using helm and usage of ExternalSecrets in your Kubernetes cluster. <br><br>
**Prerequisites** <br>
&emsp;•&emsp;Kubernetes cluster version 1.16.0 or above.<br>
&emsp;•&emsp;Helm installed on your local machine.<br>
&emsp;•&emsp;kubectl command-line tool.<br><br>
**Introduction** <br>
The External Secrets Operator extends Kubernetes with Custom Resources, which define where secrets live and how to synchronize them. The operator fetches secrets from external APIs and creates Kubernetes secrets. This allows you to centralize secret management.<br><br>
By following the below steps, we can seamlessly integrate ExternalSecrets(AWS SM) with our `Kubernetes cluster` to manage secrets from external providers like `AWS Secrets Manager`. This setup ensures that your secrets are managed securely and efficiently, reducing the risk of exposing sensitive information.<br><br>
&emsp;1.&emsp; **Install ExternalSecrets** <br>
First, let’s add the ExternalSecrets Helm repository.<br>
```hcl
    helm repo add external-secrets https://charts.external-secrets.io
```
**Install from Chart Repository** <br>
The default installation options will automatically install and manage the `CustomResourceDefinitions` (CRDs) required by ExternalSecrets. If you prefer to manage the CRDs manually, you can disable this by setting the installCRDs option to false(`-- set installCRDs=false`).
```hcl
helm install external-secrets \
   external-secrets/external-secrets \
   -n external-secrets \
   --create-namespace
```
Verify the external secrets installation by running the below command: <br>
```hcl
    kubectl get pods,crd -n external-secrets
```
It will create the three different custom controllers:<br>

&emsp;•&emsp;**external-secrets:** This is the main controller responsible for managing ExternalSecret resources. It watches for changes in ExternalSecret resources and handles the syncing of secrets from external secret stores into Kubernetes Secrets.<br>
&emsp;•&emsp;**external-secrets-cert-controller:** This controller is likely responsible for managing certificates related to External Secrets. It may handle tasks such as certificate rotation or ensuring that TLS connections are properly configured.<br>
&emsp;•&emsp;**external-secrets-webhook:** This controller is likely related to managing webhooks for External Secrets. It may handle tasks such as validating ExternalSecret resources or performing additional actions when ExternalSecret resources are created or updated.<br><br>
Each of these controllers plays a specific role in the lifecycle of ExternalSecret resources within your Kubernetes cluster.<br><br>
&emsp;2.&emsp; **Create secret in AWS SM**<br>
The CloudFormation template provided provisions an AWS Secrets Manager secret named `“My-First-SM-Secret”`, containing a username and password. Additionally, it creates an IAM user named `“awssm-k8s-user”` and attaches a policy called `“AWSSM-Read-Policy”` to this user. This policy grants the read permissions for secrets stored in AWS Secrets Manager.<br><br>
```hcl
# Owner: Anvesh Muppeda
# The CloudFormation template provided provisions an AWS Secrets Manager secret named
# "My-First-SM-Secret", containing a username and password. 
# Additionally, it creates an IAM user named "awssm-k8s-user" 
# and attaches a policy called "AWSSM-Read-Policy" to this user. This policy grants 
# permissions for various actions on secrets stored in AWS Secrets Manager, including    # retrieving secret values, listing secrets, and describing secrets. 
# Finally, the template includes outputs for the ARN of the created secret 
# and the name of the IAM user.

AWSTemplateFormatVersion: '2010-09-09'
Resources:
  MySecret:
    Type: "AWS::SecretsManager::Secret"
    Properties: 
      Name: "My-First-SM-Secret"
      SecretString: !Sub |
        {
          "username": "anvesh",
          "password": "anveshpassword"
        }
  AWSSMUser:
    Type: "AWS::IAM::User"
    Properties:
      UserName: "awssm-k8s-user"

  SMReadPolicy:
    Type: "AWS::IAM::Policy"
    Properties:
      PolicyName: "AWSSM-Read-Policy"
      Users: 
        - !Ref AWSSMUser
      PolicyDocument: 
        Version: "2012-10-17"
        Statement: 
          - Effect: "Allow"
            Action: 
              - "secretsmanager:GetRandomPassword"
              - "secretsmanager:GetResourcePolicy"
              - "secretsmanager:GetSecretValue"
              - "secretsmanager:DescribeSecret"
              - "secretsmanager:ListSecretVersionIds"
              - "secretsmanager:ListSecrets"
              - "secretsmanager:BatchGetSecretValue"
            Resource: !Sub "arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:*"

Outputs:
  SecretARN:
    Description: "The ARN of the created secret"
    Value: !Ref MySecret
  IAMUserName:
    Description: "The name of the created IAM user"
    Value: !Ref AWSSMUser
```
Once you have created the secret on AWS SM and IAM user then create the `ACCESS KEYS` and `SECRET KEYS` for kubernetes to authenticate the AWS SM <br><br>
&emsp;3.&emsp; **Create AWS Credentials Secret** <br><br>
Next, we’ll create a Kubernetes secret containing your AWS credentials.<br>

&emsp;&emsp;1.&emsp; **Encode the Keys in Base64** <br>
&emsp;&emsp;&emsp;First, encode your `KEYID` and `SECRETKEY` in base64. You can do this using the following commands: <br>
```hcl
echo -n 'access-key' | base64
echo -n 'secret-access-key' | base64
```
Replace `access-key` and `secret-access-key` with your actual AWS access key ID and secret access key.<br>
&emsp;&emsp;&emsp;Let’s assume the base64-encoded values are:<br>

&emsp;&emsp;&emsp;KEYID encoded: S0VZSUQ=<br>
&emsp;&emsp;&emsp;SECRETKEY encoded: U0VDUkVUS0VZ<br><br>
&emsp;&emsp;2.&emsp; **Create the YAML Manifest**<br>
Now, create a file named aws-iam-secret.yaml and add the following content:<br>
```hcl
apiVersion: v1
kind: Secret
metadata:
  name: aws-iam-secret
type: Opaque
data:
  access-key: S0VZSUQ=
  secret-access-key: U0VDUkVUS0VZ
```
&emsp;&emsp;3.&emsp; **Apply the Manifest** <br>
Apply the manifest using `kubectl apply`:<br>
```hcl
    kubectl apply -f aws-iam-secret.yaml
```
&emsp;&emsp;4.&emsp; **Create a SecretStore**<br>
Create a YAML file named basic-secret-store.yaml with the following content:<br>
```hcl
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-secretstore
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1
      auth:
        secretRef:
          accessKeyIDSecretRef:
            name: aws-iam-secret
            key: access-key
          secretAccessKeySecretRef:
            name: aws-iam-secret
            key: secret-access-key
```
This YAML manifest defines a SecretStore named `“aws-secretstore”` that instructs External Secrets to interact with AWS Secrets Manager in the `“us-east-1”` region. It retrieves AWS access credentials from a Kubernetes secret named `“aws-iam-secret”` to authenticate and access secrets within Secrets Manager.<br><br>
Apply this configuration to create the SecretStore resource.<br>
```hcl
    kubectl apply -f "basic-secret-store.yaml"
```
&emsp;&emsp;5.&emsp; **Create an ExternalSecret** <br>
Now, create a YAML file named basic-external-secret.yaml with the following content:<br>
```hcl
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: my-first-externalsecret
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secretstore
    kind: SecretStore
  target:
    name: aws-sm-secret
    creationPolicy: Owner
  dataFrom:
  - extract:
      key: My-First-SM-Secret
```
This YAML manifest defines an ExternalSecret named `“my-first-externalsecret”` that periodically refreshes secrets every 1 hour. It references a SecretStore named `“aws-secretstore”` to retrieve secrets from AWS Secrets Manager. The retrieved secret `“My-First-SM-Secret”` is stored in a Kubernetes secret named `“aws-sm-secret”`.<br><br>
Apply this configuration to create the SecretStore resource.<br>
```hcl
    kubectl apply -f "basic-external-secret.yaml"
```
